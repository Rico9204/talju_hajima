# 워크스페이스 텍스트 추출·검색 개선 메모

2026-09-17 진단. 사용자가 이후 개선 작업에서 참고하도록 보관을 요청함.
현재 구현을 기준으로 한 평가이며, 아래 개선안은 아직 구현되지 않았다. 대용량 성능 측정은 수행하지 않았다.

## 현재 구조

- 브라우저에서 텍스트를 추출한 뒤 원본을 Supabase Storage에 업로드하고, `file_versions.search_text`와 `search_status`에 버전별 결과를 저장한다.
- PDF.js로 PDF를 추출한다. 최대 100페이지·20만 자·30초 제한이 있으며 일부만 처리되면 partial 상태가 된다.
- TXT·MD·CSV·JSON 등 텍스트 파일을 지원한다. Word(DOC/DOCX), Office 문서 및 스캔 문서 OCR은 지원하지 않는다.
- DB 검색 인덱스나 검색 RPC 없이 브라우저에서 문자열 포함 여부로 검색한다. 본문 검색은 현재 버전만 대상으로 한다.
- 파일 목록 조회는 모든 버전의 추출 본문까지 가져온다. 활동 동기화에서도 약 30초마다 목록 조회가 반복된다.
- PDF 미리보기는 원본을 다시 읽어 텍스트 레이어에 검색어를 표시한다. DB에 페이지별 본문이나 위치 정보가 없어 검색 결과에서 일치 페이지로 이동하는 기능은 없다.
- 추출 본문 갱신 RPC는 활성 프로젝트 구성원에게 허용되어 있다. 원본과 추출 결과의 일치 여부는 서버에서 검증하지 않는다.

## 유지할 장점

- 원본 바이너리를 DB 본문과 분리해 비공개 Storage에 저장한다.
- 추출 내용을 파일 버전에 연결하므로 현재 버전 변경과 검색 대상을 함께 관리할 수 있다.
- 프로젝트 접근 권한, 버전 삭제에 따른 데이터 정리, 추출 상태 및 재처리 흐름이 존재한다.
- 하이라이트를 HTML 문자열 삽입이 아닌 React 텍스트 렌더링으로 처리한다.

## 권장 개선 순서

1. **목록 조회 경량화 및 DB 검색**
   - 목록은 파일명·태그·크기·버전·분석 상태 중심으로 조회하고 전체 본문을 제외한다.
   - 프로젝트 접근 권한과 현재 버전을 확인하는 검색 RPC를 추가한다.
   - 검색 결과는 페이지 단위로 반환하고, 일치 위치 주변의 짧은 발췌만 전달한다. 전체 본문은 선택 시 조회한다.
   - 부분 문자열 검색에는 PostgreSQL `pg_trgm` + GIN 인덱스를 우선 검토한다. 짧은 한국어 검색어는 효과가 제한될 수 있으므로 실제 문서로 검증한다.
   - `tsvector` 전문 검색은 관련도 정렬 등의 요구에 따라 검토하되 한국어 형태소 분석을 자동으로 제공한다고 가정하지 않는다.
2. **비동기 추출 및 Word 지원**
   - 원본 업로드 후 별도 작업자가 추출하도록 분리한다. 대기·처리 중·완료·부분 완료·실패 상태와 재시도를 관리한다.
   - 결과는 업로드 당시의 버전 ID에 연결한다. 작업 중 파일 삭제나 현재 버전 변경이 발생해도 다른 버전을 덮어쓰지 않도록 한다.
   - 결과 저장 권한을 작업자로 제한하고 원본 해시·파서 버전·처리 시각·오류 정보를 기록한다.
   - Word 등 다양한 형식은 Apache Tika 또는 형식별 파서를 검토한다. Tika는 별도 실행 환경 운영 비용을 고려한다.
3. **페이지·문단 저장 및 하이라이트 개선**
   - 별도 본문 테이블에 버전 ID, 페이지 번호/문단 순서, 원문, 검색용 정규화 텍스트, 원문 위치 정보를 저장한다.
   - 공백·줄바꿈 정규화 후에도 원문 위치로 역매핑할 수 있도록 설계한다.
   - PDF는 일치 페이지로 이동하도록 개선한다. Word는 문단 기준으로 시작하며 정확한 페이지 표시는 별도 렌더링/PDF 변환이 필요하다.
4. **선택적 OCR**
   - 스캔 PDF와 이미지에서 텍스트가 필요한 경우 추가한다. 자원 비용과 한국어 인식 정확도를 별도로 평가한다.

기존 Supabase와 버전별 원본 저장 구조를 유지하면서 위 순서로 개선하는 방안을 권장한다. 벡터 검색은 현재 요구에서 우선순위가 낮다.
